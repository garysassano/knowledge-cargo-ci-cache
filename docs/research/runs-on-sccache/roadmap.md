# RunsOn sccache research roadmap

Status: Proposed work, not completed implementation or released service features. This is the sole task inventory for the research collection. Design pages own contracts and alternatives; [validation](validation.md) owns qualification tests. Task IDs are stable references, not release phases.

Start from the [versioned implementation reference](../../reference/compiler-cache-implementation.md), [current deployment](../../deployments/runs-on/README.md), and [limited performance model](../../evidence/cache-strategy-benchmarks.md#planning-model). None of the proposed gains is established by hit rate or a transport microbenchmark alone.

## Measure existing controls first

These experiments can determine whether larger implementation work is worthwhile. Keep the existing direct-compiler and default-server S3 workflows as controls; do not silently add unimplemented readiness or broker behavior to them.

| ID  | Experiment and completion evidence                                                                                                                                                                                                                   |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M1  | Establish repeatable direct-`rustc`, cold population, warm exact, changed-source, and empty read-only comparisons. Apply the [measurement procedure](../../operations/measuring-cache-performance.md), including paired sampling and stopping rules. |
| M2  | Repeat the separate Cargo-input archive ablation. Compare dependency-download savings with the archive's complete setup, restore, and post overhead; the existing single-run result is a hypothesis to reproduce.                                    |
| M3  | Compare the released object-age retention with candidate 30- and 60-day policies. Measure reuse distance, warm frequency, stored bytes, requests, and total cost before selecting a value.                                                           |
| M4  | Compare an exact binary preinstalled in the runner image with installation during each job. Include image maintenance and complete setup time.                                                                                                       |
| M5  | Vary Cargo `--jobs` and remote-request concurrency independently. Measure complete job time, memory, origin pressure, and tails across cache states.                                                                                                 |
| M6  | Compare supported zstd levels, beginning with 1 and 3 and extending to 6 and 9 only if useful. Record CPU, stored bytes, transfer, and format compatibility.                                                                                         |

The workflow or measurement repository owns M1–M6; M3 also needs RunsOn stack configuration and M4 needs runner-image ownership. [Direct S3 performance](direct-s3-performance.md) defines instrumentation and tuning dimensions.

## Qualify larger experiments only when needed

Attempt L1 after lifecycle and ownership are available. A directly managed sticky tier can precede a gateway; a gateway-managed tier depends on the corresponding gateway work. Prototype G1 as read-only pass-through and measure each subsequent optimization separately.

| ID  | Experiment                                                                                                          | Prerequisites and completion evidence                                                                                                                                                                                                                |
| --- | ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| L1  | [Sticky local sccache](sticky-local-tier.md), local-only or `disk,s3` with shared S3 fallback.                      | A1, U1, and I1 publication fencing; G3 if gateway-managed. Prove single ownership, crash-consistent snapshots, bounded GC, and total savings after restore/save costs.                                                                               |
| G1  | [WebDAV gateway](gateway.md) pass-through, typed results, bounded requests, and session control.                    | C1, I1, and A1 integration. Establish protocol conformance and cache-disabled overhead before adding cache features.                                                                                                                                 |
| G2  | Gateway negative lookup metadata, same-key coalescing, L0, and eventually immutable packs with range reads.         | G1; C1 publication rules for authoritative membership. Measure avoided requests, useful/wasted bytes, index or pack construction, and complete job time for each feature.                                                                            |
| G3  | Gateway conditional remote writes, bounded queues, drain, and publication; deferred replay only if justified.       | G1, U1/U4 where the upstream path is used, and I1 authority. Start with synchronous remote commit; qualify any later replay failure domain separately.                                                                                               |
| B1  | [S3 Express](alternative-backends.md#s3-express-one-zone), read-only first.                                         | O1, same-AZ placement, endpoints/session support, fallback, and complete cost measurement. Canonical writes additionally need verified conditional creation and publication fencing; a gateway is required only if that is the selected integration. |
| B2  | [Redis, Valkey, or Memcached](alternative-backends.md#redis-valkey-and-memcached) as a shared hot tier.             | Pursue only if simpler storage leaves material latency. Measure eviction, failover, persistence, isolation, and service/operational cost. Memcached cannot own canonical durability.                                                                 |
| B3  | [Native GHA through Magic Cache](alternative-backends.md#native-github-actions-cache-through-magic-cache).          | O1 and fresh-job visibility. Treat protocol isolation enabled and disabled as distinct namespace populations.                                                                                                                                        |
| R1  | This archive: publish sanitized evidence and update decisions, history, deployment guidance, and copyable examples. | Implemented feature and [promotion gates](validation.md#promotion-gates); follow the [maintenance checklist](../../operations/maintenance-checklist.md).                                                                                             |

## Open choices

Resolve these through the linked design and measured workload requirements, not by treating the roadmap as a product specification.

| Choice                           | Alternatives and deciding evidence                                                                                                                                |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Gateway protocol and authority   | WebDAV, loopback S3, or an upstream backend; brokered STS or a remote proxy. Compare protocol fit, root-capable job isolation, overhead, and operational cost.    |
| Membership representation        | Bloom/Xor filters, sorted shards, DynamoDB, Redis, or Valkey. Measure cardinality, memory, build/download cost, and mutable-versus-sealed correctness.            |
| Write acknowledgement            | Remote commit initially; remotely authorized deferred replay only with an explicit failure domain and audited ownership.                                          |
| Sticky publication               | One fenced publisher, read-only/copy-on-write consumers, or partitioned lineages. Choose from concurrency and hot-set overlap.                                    |
| Namespace, format, and retention | Select digest inputs, schema, compression, and lifetime from trust boundaries, compatibility, reuse distance, and cost.                                           |
| PR access and strict mode        | Select read-only versus disabled from confidentiality policy; select fallback versus failure from workload and population ownership.                              |
| Express writer coordination      | Use client-supported conditional creation, an external reservation mechanism if required, or no canonical writer mode. Test contention and stale-writer recovery. |
| Acceptance budgets               | Predeclare project-specific effect size, latency deadlines, uncertainty, and cost per saved minute. No universal numeric promotion threshold is adopted here.     |

## Deprioritized directions

Keep client-side daemon bypass out of the default path unless new paired evidence justifies it. WebDAV is a storage protocol and can use normal sccache server mode; it does not require `SCCACHE_CLIENT_SIDE=1`.

Do not repeat ephemeral multilevel trials without persistence and write accounting, infer native GHA compatibility from archive-cache support, or put a mutable local `SCCACHE_DIR` on a concurrently mounted shared filesystem. Keep larger services, packs, prefetch, and additional tiers behind independently measured experiments.
